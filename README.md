## Часть 2. Разбиение на компоненты и хуки

> Для преобразования `HTML` в `JSX` используйте этот [ сервис ](https://transform.tools/html-to-jsx)

Создайте по одному `.jsx`-файлу на каждый компонент из вашего дерева:

1. **`ViewSwitch`** — две кнопки-таба «Моя полка» / «Статистика». Не хранит состояние сам, подсвечивает активный экран на основе пропа `currentScreen`, по клику вызывает `onChange(screenName)`.
2. **`BookForm`** — контролируемый `input` с собственным `useState` для черновика названия. По кнопке «Добавить на полку» или `Enter` вызывает `onAdd(title)` и очищает своё поле. Пустая/пробельная строка не отправляется.
3. **`FilterChip`** — чекбокс-«таблетка» без собственного состояния: `checked` и `onChange` приходят пропсами из `ShelfScreen`.
4. **`BookItem`** — одна книга: цветная обложка-заглушка (можно взять цвет по остатку от деления `id` на длину палитры — как в референсе), название, автор, переключатель «Прочитано» (`onToggleRead`) и кнопка удаления (`onDelete`). Не знает, что такое фильтрация — просто рендерит то, что получил.
5. **`BookList`** — принимает уже отфильтрованный массив `books` и рендерит `BookItem` через `.map()` с `key={book.id}`. Сама фильтрацию не делает.
6. **`ShelfScreen`** — держит логику фильтрации (`books.filter(...)` на основе пропа `showOnlyUnread`) и раздаёт колбэки вниз.
7. **`StatsSummary`** — принимает `books`, считает `total`/`unread`/`read` прямо в теле компонента (без `useState` — это derived-значение).
8. **`ReadingCounter`** — три кнопки; значение и обработчики приходят пропсами из `App`. Кнопка «−» задизейблена, если значение уже `0`.
9. **`StatsScreen`** — просто раскладывает `StatsSummary` и `ReadingCounter`.
10. **`App`** — единственное место, где живут все `useState`: `currentScreen`, `books`, `showOnlyUnread`, `pagesToday`. Передаёт данные и функции-обработчики вниз по дереву, сам ничего не рендерит напрямую, кроме компоновки дочерних компонентов.

**Важно:** обновления `books` должны быть иммутабельными:

- добавление — через спред (`[...books, newBook]`);
- удаление — через `.filter()`;
- переключение `read` у одной книги — через `.map()`, при этом остальные
  книги должны остаться **теми же объектами** (не пересоздавать их).

## Требования к оформлению кода

- Имя компонента и имя файла совпадают и начинаются с заглавной буквы
  (`BookItem.jsx`, а не `bookItem.jsx`).
- Каждый компонент — отдельный файл, экспортируется по умолчанию
  (`export default`).
- Внутри компонентов, принимающих пропсы, используется деструктуризация в
  параметрах функции, а не обращение через `props.что-то` по всему коду.
- Никаких прямых мутаций состояния (`books.push(...)`, `book.read = true`,
  `arr[i] = ...`) — только через `set...` с новым массивом/объектом.
- У каждого элемента списка есть `key`, построенный на основе `id` книги,
  а не на основе индекса массива.
- Значение из `useState` нигде не читается и не пишется напрямую в DOM
  (никаких `document.getElementById(...)` внутри компонентов).

# Памятка

## useState

### Синтаксис

```
const [значение, setЗначение] = useState(начальноеЗначение);
```

- `значение` — то, что читается при рендере.
- `setЗначение` — единственный правильный способ его изменить. Прямое
  присваивание (`значение = ...`) не вызовет повторный рендер и является
  ошибкой.
- Вызов `useState` должен быть на верхнем уровне компонента: не внутри
  `if`, `for` или вложенной функции.

### Базовый пример: переключение состояния (не число, а булево значение)

Похоже на счётчик, но здесь только два состояния — вкл/выкл.

```
const [isOn, setIsOn] = useState(false);

<button onClick={() => setIsOn(prev => !prev)}>
  {isOn ? 'Выключить свет' : 'Включить свет'}
</button>
```

### Функциональное обновление — когда новое значение зависит от старого

Если внутри одного обработчика вызвать `setX(x + 1)` дважды подряд, оба
вызова "увидят" одно и то же старое `x` из замыкания — в сумме получится
`+1`, а не `+2`. Чтобы React брал самое свежее значение, передавайте в
`set...` функцию, а не готовое число:

```
// Плохо: оба вызова используют одно и то же значение score из рендера
setScore(score + 10);
setScore(score + 10);

// Хорошо: каждый вызов получает актуальное значение на момент применения
setScore(prev => prev + 10);
setScore(prev => prev + 10);
```

Это же правило работает и для `setInterval`/`setTimeout` внутри
`useEffect` — там `x` тоже "застревает" на значении из момента запуска
эффекта, если не использовать функциональную форму.

### Обновление массива — без мутации

```
const [playlist, setPlaylist] = useState([]);

// добавить трек
setPlaylist(prev => [...prev, newTrack]);

// удалить трек по id
setPlaylist(prev => prev.filter(track => track.id !== id));

// пометить один трек избранным, остальные не трогать
setPlaylist(prev =>
  prev.map(track => track.id === id ? { ...track, favorite: !track.favorite } : track)
);
```

Правило простое: если структура — массив или объект, `set...` всегда
получает **новый** массив/объект. `push`, `splice`, прямое присваивание
поля (`track.favorite = true`) — так делать нельзя, React не увидит
изменения.

### Обновление объекта-формы

```
const [profile, setProfile] = useState({ name: '', city: '' });

function handleNameChange(e) {
  setProfile(prev => ({ ...prev, name: e.target.value }));
}
```

Забытый спред (`setProfile({ name: e.target.value })` без `...prev`) —
самая частая ошибка: он затирает остальные поля объекта.

### Когда НЕ нужен отдельный useState

Если значение можно посчитать прямо при рендере из уже существующего
state — не заводите под него ещё один `useState`.

```
const [cartItems, setCartItems] = useState([]);

// Не нужно: const [totalCount, setTotalCount] = useState(0);
// Просто считаем при рендере:
const totalCount = cartItems.length;
const totalPrice = cartItems.reduce((sum, item) => sum + item.price, 0);
```

## useEffect

### Синтаксис

```
useEffect(() => {
  // код эффекта — выполняется после рендера
  return () => {
    // необязательный cleanup — выполняется перед следующим запуском
    // эффекта и перед размонтированием компонента
  };
}, [зависимости]);
```

### Три формы второго аргумента

| Второй аргумент | Когда срабатывает                                                    |
| --------------- | -------------------------------------------------------------------- |
| не передан      | после **каждого** рендера                                            |
| `[]`            | один раз, после первого рендера (монтирование)                       |
| `[a, b]`        | после первого рендера и затем каждый раз, когда `a` или `b` меняются |

### Пример: без зависимостей — логирование каждого рендера

```
useEffect(() => {
  console.log('Компонент отрендерился');
});
```

Полезно для отладки, но в реальном коде почти всегда нужен второй
аргумент — иначе эффект будет срабатывать без остановки.

### Пример: пустой массив — что-то один раз при монтировании

```
useEffect(() => {
  document.title = 'Открыто новое окно чата';
}, []);
```

### Пример: с зависимостью — реакция на конкретное изменение

```
useEffect(() => {
  console.log(`Пользователь открыл раздел: ${activeTab}`);
}, [activeTab]);
```

Сработает только когда поменяется именно `activeTab`, а не при любом
другом обновлении state в этом же компоненте.

### Пример: debounce

```
useEffect(() => {
  const timer = setTimeout(() => {
    ...
  }, 400);

  return () => clearTimeout(timer);
}, [query]);
```

Каждое новое нажатие клавиши отменяет предыдущий незавершённый таймер —
запрос улетает только когда пользователь на 400мс перестал печатать.
